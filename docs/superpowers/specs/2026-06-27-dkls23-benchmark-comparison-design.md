# DKLs23 Benchmark & Cross-Implementation Comparison — Design

- **Date:** 2026-06-27
- **Status:** Approved (design); pending implementation plan
- **Branch:** `bench/dkls23-comparison` (off `dev`)
- **Author:** k0yote (with Claude)

## 1. Context & Motivation

`kawasekit-dkls23` is a hardened fork of `0xCarbon/DKLs23` (threshold-ECDSA, eprint
2023/765) backing a 2-of-2 co-signer. The fork has diverged from upstream through a
self-hardening cycle (ToB-methodology findings H1/M1/M2/L1–L4 plus follow-ups: root
agreement, constant-time selects, protocol-version checks, abort-taxonomy changes,
zeroize, `itertools::zip_eq`, etc.).

Because the security-critical code paths were *changed*, we want two things that the
existing test suite alone does not present in a consumable form:

1. **A correctness proof** — demonstrate that, after the changes, a full distributed
   key generation + signing produces an ECDSA signature that verifies under a standard
   verifier. ("It still works properly.")
2. **A performance benchmark** — measure DKG, signing, and refresh cost, and compare
   the fork against upstream `0xCarbon/DKLs23` and the independent
   `silence-laboratories/dkls23` implementation.

## 2. Goals / Non-Goals

### Goals
- A reusable, reproducible benchmark harness committed to the repo.
- Time, on-the-wire message size, and round count for DKG / signing / refresh, on both
  secp256k1 and secp256r1, at a 2-of-2 configuration.
- A controlled fork-vs-upstream comparison that isolates the cost of the fork's changes.
- An indicative fork-vs-silence-laboratories comparison.
- A runnable correctness artifact (`examples/verify_e2e.rs`).
- A `docs/BENCHMARKS.md` report with methodology, results, and honesty caveats.

### Non-Goals
- **Not** a security claim of any kind. Benchmarks measure speed; they say nothing about
  correctness-of-protocol or cryptographic safety. The mandatory third-party audit is
  unaffected by anything in this work.
- **Not** cross-implementation interoperability (we do not attempt to have one
  implementation sign a key generated by another).
- **Not** a network/transport benchmark. Timings are in-process (compute-only); network
  cost is represented indirectly via message bytes and round counts.
- **Not** a sweep over many (t, n) configurations. Scope is fixed at 2-of-2. (2-of-3 etc.
  is a trivial future extension of the same harness.)

## 3. Honesty Constraints (must appear in `docs/BENCHMARKS.md`)

These are load-bearing and reflect the project's standing "honesty ceiling":

- **perf ≠ correctness ≠ security.** A fast implementation can still be wrong or unsafe.
- **fork ↔ 0xCarbon = controlled.** Identical crate layout and identical dependency pins
  (`elliptic-curve 0.14.0-rc.4`, `k256 0.14.0-rc.7`, version 0.5.1) mean any measured
  delta is attributable to the fork's protocol changes, not to a dependency difference.
- **fork ↔ silence-laboratories = indicative only.** Different implementation, API,
  abstractions, message-validation strictness, and proof parameters. Same hardware and a
  workload mapped as closely as possible, but it is not a controlled experiment.
- **in-process / compute-only.** Serialization is excluded from the timed path; bytes and
  rounds are measured separately.
- **UNAUDITED status is unchanged.** This work does not reduce the need for a third-party
  cryptographic audit before any real value.

## 4. Scope

| Dimension | Value |
|---|---|
| Operations | DKG (keygen), Signing, Refresh (both `refresh_complete` and `refresh_fast`) |
| Curves | secp256k1 (`k256::Secp256k1`) and secp256r1 (`p256::NistP256`) |
| Threshold config | 2-of-2 only |
| Implementations | fork (`kawasekit-dkls23`), `0xCarbon/DKLs23@dev`, `silence-laboratories/dkls23@main` |

## 5. Feasibility (verified against current code)

The full protocol is driven phase-by-phase with explicit message routing between parties.
The existing in-crate tests `test_dkg_and_signing` (full DKG → sign) and
`test_signing_against_ecdsa` (sign → verify under a standard ECDSA verifier) are the
orchestration templates.

All driver types and entry points needed to drive the protocol from an **external** crate
are `pub`, so the benchmark crate does **not** need to touch any audited library `src/`:

- `dkg::{phase1, phase2, phase3, phase4}` (free fns, generic over `C: DklsCurve`)
- `Party::{sign_phase1, sign_phase2, sign_phase3, sign_phase4}`
- `Party::{refresh_complete_phase1..4, refresh_phase1..4}`
- Driver structs: `SessionData`, `SignData`, `Parameters`, `PartyIndex`,
  `UniqueKeep1to2`, `KeepPhase1to2`, `TransmitPhase1to2`, `UniqueKeep2to3`,
  `Broadcast3to4`, and the DKG keep/transmit types.
- `verify_ecdsa_signature::<C>(...)` (the standard-ECDSA correctness verifier)
- `EcdsaSignature::{to_bytes, to_bytes_with_recovery}`
- `serde` is a **default** feature, so message-size accounting (serialize each transmit,
  sum bytes) works without extra configuration.

## 6. Architecture

### 6.1 New workspace member: `dkls23-benchmarks`
- A new crate added to the workspace `members`, marked `publish = false`.
- Dependencies: `dkls23-secp256k1`, `dkls23-secp256r1`, `criterion`, plus `serde`/`bincode`
  (via the curve crates' default features) for byte accounting.
- **Touches no library `src/`** → the doc-citation lock (`tools/check_doc_citations.py`,
  scoped to `docs/audit-context.md`) is unaffected, consistent with project convention.

### 6.2 Generic harness (DRY, curve-parameterized)
A support module exposes one helper per operation, generic over `C: DklsCurve`, mirroring
the test orchestration:

- `run_dkg<C>(params, session_id) -> Vec<Party<C>>`
- `run_sign<C>(parties, executing, sign_id, message_hash) -> EcdsaSignature`
- `run_refresh_complete<C>(parties, ...) -> Vec<Party<C>>`
- `run_refresh_fast<C>(parties, ...) -> Vec<Party<C>>`
- `wire_size_of(&messages) -> usize` and round-count accounting helpers

secp256k1 vs secp256r1 differ only by the type argument (`k256::Secp256k1` /
`p256::NistP256`). DKG-derived parties are produced by `run_dkg` (no trusted-dealer
shortcut in the measured path); `re_key` / `trusted-dealer-import` is **not** required.

### 6.3 Criterion benchmark groups
Groups, each at 2-of-2, each run for `{k1, r1}`:
- `dkg` — full 4-phase keygen (measured end to end).
- `sign` — signing phases only; parties are produced by `run_dkg` in criterion's
  **setup closure** (`iter_batched`, not measured).
- `refresh_complete` — full proactive refresh.
- `refresh_fast` — fast proactive refresh.

### 6.4 Metrics binary (bandwidth)
A small `main.rs` (not criterion) runs each operation once, serializes every transmit
message via the default `serde`/`bincode` path, and emits **total bytes on the wire +
round count** per operation/curve as JSON **plus** a Markdown table fragment (for pasting
into `docs/BENCHMARKS.md`). This mirrors `silence-laboratories/dkls23`'s own
`crates/dkls-metrics` approach and keeps serialization out of the timed path.

### 6.5 Correctness example
`examples/verify_e2e.rs` lives in the `dkls23-benchmarks` crate (which already depends on
both curve crates, so it can call their address-derivation functions). It runs a full
2-of-2 DKG → sign, calls `verify_ecdsa_signature`, derives the chain address, and prints a
clear PASS/FAIL. A runnable, auditable proof artifact distinct from the timing benches.
Keeping it in the `publish = false` bench crate preserves the "no changes to the published
library crates" principle.

## 7. What Is Measured

| Metric | How | In timed path? |
|---|---|---|
| Wall-clock time | criterion median + dispersion, release build | yes |
| Message bytes | serialize transmits (serde/bincode), sum | no (separate) |
| Round count | static per operation, reported in the table | no (separate) |

## 8. Methodology (recorded in `docs/BENCHMARKS.md` header)
- Build: `cargo bench` (release). `RUSTFLAGS="-C target-cpu=native"`.
- Record: rustc version, CPU model, OS, criterion sample size, 2-of-2, in-process
  (no network), compute-only timings.
- All three implementations run on the **same machine** in the same session.

## 9. Phased Plan

### Phase 0 — Correctness gate (distinct from benchmarking)
- Confirm `test_signing_against_ecdsa` and `test_dkg_and_signing` pass on both curves. The
  existing suite already verifies produced signatures against a standard ECDSA verifier, so
  this is the core "it works properly" proof.
- The runnable `examples/verify_e2e.rs` artifact is delivered in Phase 1 (it needs the
  `dkls23-benchmarks` crate to exist); Phase 0 is the test-based confirmation.

### Phase 1 — Fork-internal benches + metrics
- Implement the `dkls23-benchmarks` crate (§6) and the metrics binary.
- Produce the fork's own numbers (time + bytes + rounds) for all operations/curves.
- Independently valuable and entirely under our control. Commit to the repo.

### Phase 2 — Cross-implementation comparison (clones live in scratchpad, not committed)
- **0xCarbon `dev`:** identical crate names/layout/deps → the same harness compiles with
  near-zero change. **Risk:** the fork added fields/echoes absent upstream (H1
  `root_digest` echo on the phase-1 transmit, M2 `protocol_version` fields). The upstream
  variant of each helper gets a thin shim where signatures differ. Result = clean delta =
  cost of the fork's changes.
- **silence-laboratories `main`:** different API → run **their** existing
  `crates/dkls-metrics` benches on the same machine and map their workload to ours.
  Indicative comparison.
- Aggregate everything into `docs/BENCHMARKS.md`.

## 10. `docs/BENCHMARKS.md` Structure
1. Methodology header (§8).
2. Honesty caveats (§3) — up front.
3. One table per operation: rows = implementation, columns per curve = median time,
   message bytes, round count.
4. Short interpretation, explicitly labeling the silence-laboratories column as indicative.

## 11. Deliverables
1. `dkls23-benchmarks/` crate (criterion benches + metrics binary) — committed.
2. `examples/verify_e2e.rs` — committed.
3. `docs/BENCHMARKS.md` — committed.

## 12. Risks & Mitigations
- **Upstream API divergence** (Phase 2 / 0xCarbon): thin per-helper shim for the differing
  signatures; documented in `BENCHMARKS.md`.
- **silence-laboratories API mismatch:** use their own harness rather than forcing ours;
  label results indicative.
- **Dependency conflict if all three were one workspace:** avoided — each implementation is
  built/run in its own context (the fork in-repo; upstream and silence-labs as separate
  scratchpad checkouts), never as co-resident dependencies.
- **Criterion `iter_batched` setup cost** (re-running DKG per batch for `sign`): acceptable
  at 2-of-2; setup is not part of the measured time.
