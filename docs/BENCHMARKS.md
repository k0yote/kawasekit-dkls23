# DKLs23 Benchmarks

> **perf ≠ correctness ≠ security.** These numbers measure *speed and message size only*.
> They say nothing about cryptographic correctness or safety. This fork remains
> **UNAUDITED**; a third-party cryptographic audit is mandatory before real value. Nothing
> in this document reduces that requirement.

Generated by the in-repo `dkls23-benchmarks` crate, which drives DKG / signing / refresh
through the public API only (no library `src/` is involved in producing these numbers).
Reproduce with `cargo bench -p dkls23-benchmarks` and `cargo run -p dkls23-benchmarks --bin metrics --release`.

## Methodology

- **Host:** Apple M4 Pro (12 cores), 24 GB, macOS 26.5.1 (25F80).
- **Toolchain:** `rustc 1.96.0 (2026-05-25)`, `RUSTFLAGS="-C target-cpu=native"`, release build.
- **Sampling:** criterion, 100 samples per benchmark; the reported figure is the criterion median (point estimate).
- **Config:** 2-of-2. **In-process, no network** — timings are compute-only. Message bytes /
  rounds are measured separately (serialization is excluded from the timed path).
- **Message-byte metric:** total `bincode`-serialized size of the point-to-point round
  messages produced (each produced message counted once); broadcasts/commitments are not
  included, so this is the dominant-term wire cost, not a full transport accounting.
  Rounds = communication rounds.
- **Implementations:**
  - `kawasekit-dkls23` (this fork) @ `3221a8e`
  - `0xCarbon/DKLs23` @ `a0ac4d0` (`dev`) — **controlled**: identical crate layout and an
    identical resolved dependency tree (both compiled `k256 0.14.0-rc.8`, `elliptic-curve
    0.14.0-rc.29`, `p256 0.14.0-rc.8` — the shared `0.14.0-rc.7` pin resolves to `rc.8`), so
    the *same* harness compiled against it with no shim.
  - `silence-laboratories/dkls23` @ `9074cd9` (`main`) — **indicative / not reproduced** (see below).

## Honesty caveats

- **fork ↔ 0xCarbon is a controlled experiment.** Same layout, same deps, same harness →
  any timing delta is attributable to the fork's protocol changes, not to a dependency or
  harness difference. The deltas below are within run-to-run measurement noise (see the
  variance note), so the conclusion is: **the fork's hardening (ToB H1/M1/M2/L*) adds no
  measurable runtime cost.** The one real cost is on the wire (+68 B on signing — below).
- **silence-laboratories is indicative only, and was not reproduced on this host.** It is an
  independent implementation with a *fundamentally different measurement model* (async, run
  through a message relay) and a different curve-arithmetic version (`k256 0.13.4`), and it
  is secp256k1-focused. Its `main` @ `9074cd9` did not build under `rustc 1.96.0`: its code
  uses a non-generic `DLogProof` while its own locked `sl-oblivious 1.1.0` made it
  `DLogProof<C>` (a dependency drifted past the declared `1.0.0-beta`). Reproducing it would
  require patching its dependency pins, which would no longer reflect its published state —
  and even then the async+relay model is not comparable to this harness's synchronous
  compute-only timings. Their self-published benchmarks (different hardware) are at
  <https://dkls23.silencelaboratories.com/>. **Do not read the absence of a column as a
  speed claim in either direction.**
- **UNAUDITED status is unchanged** by any of this.

## Timing (criterion median, 2-of-2)

| Operation | Curve | `kawasekit-dkls23` | `0xCarbon/DKLs23` |
|---|---|---|---|
| DKG (keygen) | secp256k1 | 303.0 ms | 313.8 ms |
| DKG (keygen) | secp256r1 | 1.201 s | 1.224 s |
| Signing | secp256k1 | 4.55 ms | 4.55 ms |
| Signing | secp256r1 | 5.96 ms | 6.04 ms |
| Refresh (complete) | secp256k1 | 307.0 ms | 295.7 ms |
| Refresh (complete) | secp256r1 | 1.186 s | 1.163 s |
| Refresh (fast) | secp256k1 | 25.96 ms | 25.34 ms |
| Refresh (fast) | secp256r1 | 52.96 ms | 51.92 ms |

**Variance note (why the deltas are noise):** on the same upstream binary, `refresh_complete/secp256k1`
measured 303.7 ms and 295.7 ms on two separate runs — a 2.6 % spread larger than most
fork-vs-upstream gaps in the table. Treat any difference under ~5 % here as run-to-run noise,
not signal.

## Message size & rounds (2-of-2)

| Operation | bytes (fork) | bytes (0xCarbon) | Δ | rounds |
|---|---|---|---|---|
| DKG (keygen) | 346,462 | 346,462 | 0 | 3 |
| Signing | 187,800 | 187,732 | **+68** | 3 |
| Refresh (complete) | 346,462 | 346,462 | 0 | 3 |
| Refresh (fast) | 456 | 456 | 0 | 3 |

(Byte counts are identical for secp256k1 and secp256r1 — both are 256-bit curves and the
dominant OT-extension data is curve-independent.)

## Interpretation

- **The hardening is effectively free at runtime.** Across DKG, signing, and both refresh
  variants, on both curves, the fork tracks upstream within measurement noise. The ToB
  follow-ups (constant-time selects, root-agreement echo, protocol-version checks,
  abort-taxonomy changes) did not introduce a measurable slowdown.
- **The hardening's one concrete cost is +68 bytes on signing.** That is exactly the H1
  root-agreement echo (`root_digest`, a 32-byte `HashOutput`) plus the M2 `protocol_version`
  (`u16`, 2 bytes) added to each `TransmitPhase1to2`, times the two parties in a 2-of-2 run
  (34 B × 2 = 68 B). DKG and refresh wire sizes are unchanged. This is a deliberate,
  well-understood trade: a few dozen bytes per signing session for cross-party agreement on
  the assembled root and the protocol version (ToB TOB-SILA-7/8/11a).
- **Fast refresh is the proactive-security workhorse.** It reuses the existing OT/mul setup,
  so it costs ~456 bytes versus ~346 KB for a complete refresh (≈760× less wire), and runs
  ~12× faster on secp256k1 (26 ms vs 307 ms) and ~22× faster on secp256r1 (53 ms vs 1.19 s).
  Complete refresh ≈ DKG because it re-runs the full setup.
- **secp256r1 is ~4× slower than secp256k1** for the setup-heavy operations (DKG /
  complete refresh) — e.g. fork DKG 1.201 s vs 303 ms (3.96×) — reflecting the
  less-optimized P-256 field/scalar arithmetic on this host relative to k256. Signing and
  fast refresh, which do little curve work, are close between curves.
- **Where silence-laboratories sits** could not be measured here (build incompatibility
  above) and would in any case be indicative-only given the different model. This document
  makes no fork-vs-silence-labs speed claim.

## Correctness (separate from performance)

A benchmark proves neither correctness nor security. The "it works" evidence lives elsewhere:
`cargo run -p dkls23-benchmarks --example verify_e2e` performs a full 2-of-2 DKG → sign on
**both** curves and asserts the resulting signature verifies under the standard ECDSA
verifier (`verify_ecdsa_signature`), then derives a chain address — printing
`ALL CORRECTNESS CHECKS PASSED`. The crate's test suite (`cargo test -p dkls23-benchmarks`)
exercises the same round-trip plus pk-preservation across refresh.
